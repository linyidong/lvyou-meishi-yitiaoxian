## 4. 完成定义（DoD）

一个任务卡算「完成」必须同时满足：
1. `cd Project && npm run typecheck` exit 0（贴输出）。
2. 本计划中该卡对应 E/T 用例全部执行且「通过」（填证据）；无法自动化的填人工截图/命令输出。
3. 失败场景 §3 中与该卡相关的至少 1 条被验证（例：T-007 必验 §3-6 无权限）。
4. `git diff` 人工复核无越界文件（源码改动范围 = 任务卡「允许修改范围」）。
5. 文档同步：`docs/progress.md` 任务表 + 变更摘要、`feature-status.md`/`api-contract.md`/`known-issues.md` 对应条目更新、交接摘要（AGENTS.md §5）。
6. 汇报按 AGENTS.md §7 七段格式，区分四态；「未覆盖」如实写，禁止以 typecheck 通过冒充行为正确。
7. 涉及库写的卡（T-002/T-004）：备份证据 + 回滚演练记录在案。

## 5. 反向审查（五问书面回答）

**① 有没有遗漏的依赖或调用方？**
已按已知影响面核对：A5 删 search 前要求重跑 grep 零调用方取证（T-001 步骤①，防动态拼接漏检）；`limitsOf` 14 callers 与 `checkGuestRateLimit` 8 callers 的既有清单（module-map §4.5）已确认本计划**不触碰**这两个函数本体（T-008 只挂 UI 触点、不改配额）。潜在残留：F-52 裁剪若改变 `buildRouteSnapshot` 出参形状，其调用方（share 页 + 导出链路）需在实现时以 `codegraph callers buildRouteSnapshot` 复核——已写入 T-007 风险。**残余不确定性**：前端模板字符串拼接的 fetch 路径无法静态穷尽，靠 T-001 的删前 grep 复验兜底。

**② 有没有不必要的重构？**
没有。全部 11 卡映射 PRD §4.1 的 9 项 + 2 张支撑卡（T-011 关闭 PRD 自留的 `[待确认]`、T-006 是 F-50「两套实现各做一遍」的用户约束直接推论，非重构）。用户点名保留的 5 项（双实现/service_role/内存 Map/人工核销/不部署）零触碰；`MemberUpsellBar` 新组件属新增而非改写既有两套。

**③ 有没有更小更安全的实现？**
有两处已取小：F-52 放弃「生成图片存 Storage」方案（不引入 Supabase Storage 新依赖），改为服务端裁剪快照 + 客户端渲染精简海报；F-51 优先 pg_cron（一条迁移）而非宿主脚本（外部注册+密钥暴露面）。可再小的一处：T-004 若用户接受「后台可见即可、写回可缓一缓」，F-51 可降级为纯 T-003——但 PRD Q7 明确「要真定时任务」，故不采。

**④ 哪些结论仍缺证据？**
1. pg_cron 可用性（一条只读 SQL 即可关闭，未执行——本阶段禁连库）。
2. F-52 非会员 HTML 无完整数据的取证依赖实现后 curl 实测（用例 T-007a/E-04）。
3. PRD §7-6 幂等现状（T-011 审计对象）。
4. Playwright 在本机 macOS/Trae 沙箱的可运行性（历史有兼容教训）。
5. 手机端问题清单未走查（T-009 前置）。
6. 迁移 026 若走 pg_cron，其在自建 Envoy 网关下的 `/pg/query` 应用路径已被 025 验证，但 `CREATE EXTENSION` 需镜像内含文件——未验证。

**⑤ 回滚方案真能执行吗？**
逐卡核验：纯代码卡（T-001/003/005/006/007/008）= 单 commit `git revert`，可执行且无数据残留。配置/依赖卡（T-002 裁配置、T-010 devDeps）= revert + `npm ci` 还原 lock，可执行。库写卡（T-002 补库分支、T-004）= 前置「备份快照 + 反向 SQL + 演练通过才算 DoD」（§4-7），users 仅 3 行可逐行还原，可执行；风险点是 pg_cron 任务残留——回滚步骤含显式 `cron.unschedule`。唯 T-009 回滚粒度取决于子卡拆分（每项独立 commit 已写入步骤）。无「不可回滚」项。
