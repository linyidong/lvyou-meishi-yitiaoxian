# 项目思维逻辑（设计与取舍）

> 回答三个问题：**为什么做** / **怎么想** / **为什么这么定**。
> 最后更新：2026-10-25

## 1. 产品定位

一句话：**把「收藏夹里散落的地点」变成一条「按路顺」的行程线。**

用户真正的痛点不是"找不到好地方"，而是：
1. 收藏了几十个地点，**不知道先去哪、后去哪**
2. 每次排顺序都要开地图一个个量距离
3. 排好的行程**分享给同伴**只能截图，别人还得手动再抄一遍

所以产品只做三件事：**提取地点 → 排顺路顺序 → 出图/分享**。

## 2. 用户旅程（为什么这样设计）

```
游客试用（不登录）
   ↓ 选城市 → 设行程 → 加地点 → 调顺序 → 看地图/里程
   ↓ 想保存 → 提示登录（唯一门槛）
注册用户
   ↓ 保存路线、收藏地点、AI 提取
会员
   ↓ 每月多条路线、导入分享、导出长图
```

**关键决策：游客能走完 90% 流程，只在"保存"处要登录。**
理由：真正的价值（排线）必须先被体验到；如果一开始就要求注册，转化率会掉。代价是要防刷，所以做了免登录分桶限流（`guest-rate-limit`）：花钱接口 3 次/日、只读接口 100 次/日。

## 3. 数据模型为什么长这样

| 设计 | 原因 |
|---|---|
| `places` 是**用户级**的（带 `user_id`） | 同一个人收藏的"宽窄巷子"和别人的是两条记录，方便各自改备注/坐标 |
| 城市单独建表（109 个） | 城市是行程的强约束：排序、距离、地图中心都依赖它；也避免 AI 把"东山"识别成别的地方 |
| `routes` + `route_places` 两张表 | 一条路线可以多天，每个地点有「第几天 + 第几个 + 槽位」，支持拖动排序与"住宿点不占号位" |
| `route_shares` 存**快照** | 分享出去的内容不随原路线变化；也避免别人导入时被原主修改影响 |
| `user_daily_usage` 按 (用户, 日期, 类型) 计数 | 额度天然按天结算，查一次即可；并发用 RPC 原子累加 |
| `app_settings` 单行 JSON | 后台可改模型/开关/配额，不用改代码或重启 |

## 4. 路线排序算法

问题：给定 N 个点（N ≤ 12/天），从起点出发走一遍，总路程最短。

- **最近邻（nearest neighbor）**：每次选离当前点最近的未访问点。O(N²)，简单快，但可能"贪心走偏"
- **2-opt 改进**：反复检查"交换两条边的连接是否更短"，能跳出最近邻的局部最优
- 约束：**住宿点不占号位**、跨天分组、出发城市与实际点位分离
- 距离来自高德距离矩阵（落库缓存，避免重复计费）

为什么不用 TSP 精确解？N ≤ 12 时 2-opt 的结果在实际场景已足够好，而精确解（DP/ILP）实现复杂、边缘情况多。

## 5. AI 提取的边界处理

| 问题 | 处理 |
|---|---|
| 模型可能返回非 JSON | 解析失败 → 重试/降级提示，不让页面崩 |
| 地点不在文案城市 | 提取时同时返回 `city`，入库前按城市做**归属校验** |
| 高德同名地点在不同城市 | `citylimit=true` + **adcode 精确匹配**（区县级必须相等）；无同城结果宁可不写地址 |
| 水体/自然地名落在海里 | POI 打分（水体 −5、停车场 −3、景区 +5、有地址 +2） |
| 模型不可用 | 后台可配**备用模型**，主模型失败自动切一次 |

这几条都是"踩过坑才加的"：铜陵夜市被匹配到安徽、南门湾被标到海面、铁牛哥跑到隔壁区县。

## 6. 成本与额度控制

| 成本项 | 控制手段 |
|---|---|
| 高德 Web 服务 | Key 池轮换、距离矩阵落库缓存、免登录分桶限流、每日用量表 + 后台可见 |
| DeepSeek | 提取有次数上限（正常 10/日、会员 20/日）、输入超长截断 |
| 腾讯云 OCR | 每日次数上限（默认 20）、图片大小 7MB、不落盘 |
| 会员路线 | 正常用户 1 条/日、会员 5 条/月，RPC 内原子占额 |

原则：**花钱的路径都要有额度；额度都要能在后台看见。**

## 7. 并发与一致性

早期是"先 count 再 insert"，并发下会突破限制。后来统一改成**事务内原子操作**：

- `create_member_order_guarded`：`pg_advisory_xact_lock` → 数 pending → 插入
- `create_route_guarded`：锁 → 周期计数 → 插路线 → 累加计数
- `replace_route_places`：单事务替换（避免"先删后插"失败导致数据丢失）
- `approve_member_order`：CAS 占单，防重复核销

实测：10 并发下单只成功 2 笔、10 并发建路线只成功 1 条、同草稿 5 并发只生成 1 条路线。

## 8. 分享与导入的闭环

```
A 分享 → 生成 token + 快照 → 二维码/链接
B 打开 → 预览（标题/城市/天数/前几个地点）
      → 建成我的路线（占额度）或 只收藏（不占额度）
```

设计要点：
- **先预览再选择**：避免用户不知道要导入什么就占掉额度
- 长图二维码要能被自己的 App 识别（曾经因为二维码被画布裁切而根本扫不出，已修）
- 快照里的地点是"名字 + 类型 + 坐标"，导入时按 (用户, 城市, 名字) 去重

## 9. 长图为什么要重做

旧版长图只有文字列表，用户反馈"没有地图、太素"。
新版按**机票/登机牌**的视觉逻辑重做：票头（品牌 + logo）、行程信息行、每天一张地图截图、站点清单、撕票虚线、二维码、条形码。

为什么用 canvas 手绘而不是 html2canvas？可控性高、无额外依赖、能精确控制字体与间距；地图截图走服务端代理（避免跨域污染 canvas）。

## 10. 演进复盘（做对的 / 做错的）

**做对的**
- 游客先体验、只在保存处要登录
- 额度/成本从第一天就有表可查
- 并发问题用数据库原子操作解决，而不是应用层重试
- 测试从 0 补到 113 单测 + 8 E2E，改功能不再只靠手点

**做错的（已改）**
- 用 adcode 前 4 位判断"同城"→ 同一地级市内跨区县错配（铁牛哥）
- 关键词搜索取第一条 → 水体中心点（南门湾）
- 长图底边高度不够 → 二维码被裁切，扫不出
- 改分值没同步单测断言就提交（流程失误）
- 扫描脚本直连高德把 Key 当日配额打满（后来加了默认限额）
