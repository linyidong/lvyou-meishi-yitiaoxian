# T-054 并发残留：R3 下单软上限 + R4 建路线/转正配额

> 来源 `docs/concurrency-audit.md` §1/§4/§5。用户 2026-10-25 要求修复。

## 1. 问题

| ID | 问题 | 现状 |
|---|---|---|
| R3 | 下单 `POST /api/member/orders` 先 count 待核销再 insert，非原子；无 pending 部分唯一索引 → 并发可突破 `MAX_PENDING_ORDERS=2` | `app/api/member/orders/route.ts` |
| R4 | 建路线/游客转正：配额 check-then-act，并发窗口可超扣 1 条并建重复路线；promote 的 15s 幂等窗口在**成功后**才登记，不覆盖 in-flight 并发 | `app/api/routes/route.ts`、`app/api/try/promote/route.ts` |

## 2. 目标

1. **R3**：待核销订单数量在并发下**严格不超上限**
2. **R4**：建路线/转正配额在并发下**不超扣**；promote 并发不产生重复路线
3. 不改变现有业务语义（限额值、错误码、文案保持一致）

## 3. 实现建议（择一，需在汇报说明选择理由）

**方案 A（推荐）：事务内 `pg_advisory_xact_lock` + 计数 + 插入**
- 新增迁移 `033_concurrency_guards.sql`，两个函数：
  - `create_member_order_guarded(p_user_id uuid, p_plan text, p_amount int, p_channel text, p_note text, p_max_pending int) returns jsonb`
    - `perform pg_advisory_xact_lock(hashtext('order:' || p_user_id))`
    - 统计 pending 数量 ≥ 上限 → 返回 `{result:'LIMIT'}`
    - 否则 insert（status='pending'）→ `{result:'OK', order_id}`
  - `create_route_guarded(p_user_id uuid, p_limit int, p_payload jsonb) returns jsonb`
    - 锁 `route:'||user_id` → 按档位周期计数 → 超限 `{result:'LIMIT', remaining:0}` → 否则按 payload 插入 routes → `{result:'OK', route_id}`
- API 改为调用 RPC；错误码/文案沿用现有
- promote：在**开始处**用 `pg_advisory_xact_lock` 或先插入幂等登记行（in-flight），失败回删

**方案 B：唯一索引兜底**
- 例如 pending 订单加 `(user_id) where status='pending'` 唯一 → 只能 1 笔，与上限 2 冲突，**不适用**；若选 B 需说明如何满足"2 笔"语义

## 4. 验收标准

- [ ] **并发下单**：同一用户 10 个并发请求 → 成功数 ≤ `MAX_PENDING_ORDERS`，其余返回上限错误；库内 pending 数 = 成功数
- [ ] **并发建路线**：配额剩 1 时 10 个并发 → 只成功 1 条，库内该用户路线数不超限
- [ ] **并发 promote**：同一草稿 5 个并发 → 只生成 1 条路线
- [ ] 单请求路径行为不变（成功/失败码与文案一致）
- [ ] `typecheck` 0、`test:run` 全过、`test:e2e` 8 条通过
