# T-005 F-50 一键复位 · 游客结果页

> 由 Harness 起草，与 `docs/implementation-plan.md` T-005 对应。用户已批准计划（G5）。范围确认后实施。

## 1. 目标

`/try/result`（游客试用结果页）在用户手动调整过顺序后，提供一个「一键复位」按钮，点击即还原为系统最初推荐的顺序——**不调接口、不消耗额度、瞬间生效**。

## 2. 不做什么

- 不调用 `/api/try/order`（零请求是本任务的核心验收点）
- 不合并 `TryResultClient` 与 `RouteResultClient` 两套实现（用户明确保留）
- 不改 `/api/try/order` 的任何逻辑（含 `manual` 分支）
- 不改 `MESSAGES.ROUTE_RESULT` 既有文案的语义，只新增常量
- 不动本任务范围外的组件与页面

## 3. 背景与依据

- PRD：`docs/项目需求文档PRD.md` §4.1 新增-F50、§6、§7-5
- 用户原话（Q5）：本地恢复初始顺序，不调接口、不耗额度
- 现状证据：`Project/components/try/TryResultClient.tsx`
  - 初始顺序来源：`/api/try/order` 首次响应里的 `result.points`
  - 手动调序回路：`applyOrder()`（约 `:380-445`）→ `orderReqRef` 竞态守卫 → `draftRef.current` + `saveTryDraft()`，**不 setDraft**
  - 排序 UI：`SortablePlaceRow`（`:88`）+ `movePlace()`（`:448`）
- 教训依据：`docs/decisions.md` D-04（派生状态与 effect 的回路，禁止用 setDraft 触发重排）

## 5. 明确禁止的变更

- 不得新增任何 `fetch` / 网络请求
- 不得用 `setDraft`（会触发重排 effect 冲掉顺序，D-04）
- 不得改公共接口、不得改 `/api/try/order`
- 不得升级依赖、不得夹带重构或格式化
- 不得把复位做成「重新请求系统重排」

## 6. 实施步骤

1. 在首次 `order` 响应写入 `result` 的同一处，把该顺序快照到 `initialOrderRef`（仅在首次或重新生成后更新，手动调序不更新）
2. 派生一个「是否已偏离初始顺序」的判断（按 `sortIdOf` 比对）
3. 偏离时显示「一键复位」按钮（未偏离则禁用或隐藏）
4. 点击复位：把 `initialOrderRef` 的顺序写回 `result.points`（复用与手动调序相同的状态更新路径），同步 `draftRef` + `saveTryDraft`，地图随之重绘
5. `npm run typecheck`
6. 起 dev 手工走查（若无法登录，游客路径可直接走完三步）

## 7. 验收标准（逐条可勾）

- [ ] 游客三步走进 `/try/result`，未调序时复位按钮禁用或隐藏
- [ ] 拖动/上移下移任一地点后，复位按钮变为可用
- [ ] 点击复位后，顺序与首次进入时完全一致（含住宿点仍在序号 0）
- [ ] 点击复位期间**Network 面板零请求**（`/api/try/order` 不得出现）
- [ ] 复位后刷新页面，草稿保留复位后的顺序
- [ ] 复位后再「保存路线」跳登录，草稿顺序仍为复位后的顺序
- [ ] `npm run typecheck` exit 0
- [ ] 未新增任何网络请求、未改 `/api/try/order`、未用 `setDraft`

## 9. 人工验收
