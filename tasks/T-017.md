# T-017 修复 C9：分享页把「加载失败」误报为「链接已失效」

> 由 Harness 起草。来源：`docs/known-issues.md` C9（2026-10-22 实测：冷启动时 7.03s 超时 → 落到失效页；预热后 0.04s 正常）。

## 1. 目标

`/share/[token]` 区分三种状态：
1. **正常**：渲染分享内容（会员完整视图 / 非会员海报）
2. **确实不存在/已撤销**：显示「链接已失效」
3. **查询失败（超时/网络）**：显示「加载失败，请重试」+ 重试按钮，**不能**说"链接不存在"

## 2. 不做什么

- 不改 `route_shares` 查询条件与鉴权
- 不改分享分级（T-007）与海报逻辑
- 不改 `import` 接口
- 不调大/调小 `lib/supabase/fetch.ts` 的超时（属另一件事）

## 3. 背景与依据

- `Project/app/share/[token]/page.tsx:36-48`：`try { query } catch { share = null }` —— 异常与"查无记录"被合并成同一个 `null`，于是超时也显示「该分享链接不存在或已被作者关闭」
- 实测：冷启动 7.03s（超时）→ 失效页；预热后 0.04s → 正常
- 文案键：`MESSAGES.SHARE.linkInvalidTitle/Desc`（`config/messages.ts`）

## 4. 涉及模块与允许修改的文件

| 文件 | 允许的改动 |
|---|---|
| `Project/app/share/[token]/page.tsx` | 区分 `loadFailed` 与 `notFound` 两种状态 |
| `Project/components/share/ShareReloadButton.tsx`（新建） | 客户端重试按钮（`router.refresh()`），样式与现有按钮一致 |
| `Project/config/messages.ts` | 新增 `SHARE.loadFailedTitle / loadFailedDesc / reload` |
| `docs/known-issues.md`、`docs/progress.md`、`docs/handover/阶段7-编码-交接摘要.md` | C9 关闭 |

## 5. 明确禁止的变更

- 不得把"确实不存在"也显示成"加载失败"（两者必须分开）
- 不得改动正常路径的渲染
- 不得改用 `dynamic`/`revalidate` 绕过
- 不得整文件格式化

## 6. 实施步骤

1. `let loadFailed = false;` → 查询 `try/catch` 里 catch 设 true；若 `error` 存在也设 true
2. `notFound` 判定保持：`!share || !snapshot || !Array.isArray(dayPlans)`（仅在 `!loadFailed` 时生效）
3. `loadFailed` 分支：图标 + 「加载失败，请稍后重试」+ `<ShareReloadButton />`
4. 新增文案；重试按钮用 `useRouter().refresh()`，视觉与首页按钮一致

## 7. 验收标准

- [ ] 存在且正常的 token → 正常渲染（不回归）
- [ ] 不存在/已撤销的 token → 仍显示「链接已失效」
- [ ] 模拟查询失败（可临时把 Supabase URL 指向不可达地址，或在 dev 里注入抛错）→ 显示「加载失败」+ 有重试按钮，**不出现**"链接不存在"
- [ ] `npm run typecheck` exit 0（**不要跑 build**）

## 8. 自动化测试

| 命令 | 预期 |
|---|---|
| `npm run typecheck` | exit 0 |
| `curl /share/<不存在token>` | 页面含「链接已失效」，不含「加载失败」 |

## 9. 人工验收

用户：正常分享链接可打开；断网/超时场景（若可复现）应提示重试而非失效。
