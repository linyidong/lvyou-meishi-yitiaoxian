# T-011 幂等与并发审计（只读）

> 由 Harness 起草。来源：`docs/implementation-plan.md` T-011；PRD §7-6「重复提交/并发」标为待确认。

## 1. 目标

查清"用户重复点击 / 多标签页 / 并发请求"会不会造成数据错误，产出**风险清单 + 证据 + 建议**，不改代码。

## 2. 不做什么

- 不改任何源码、不改数据库、不加锁、不加幂等键（本任务只审计）
- 不压测、不制造并发请求打真实库（只做静态分析 + 必要的一次性只读验证）

## 3. 审计范围（逐项给结论 + 证据行号）

1. **会员下单** `POST /api/member/orders`：同一用户短时间重复提交会不会产生多笔 `pending` 订单？有没有"已有待核销订单则拒绝"的检查？
2. **核销** `PATCH /api/admin/member/orders/[id]`：管理员重复点「确认开通」会不会重复延长会员 / 重复写 `member_logs` / 重复发企微通知？状态机是否只允许 `pending → approved` 一次？
3. **保存路线** `PUT /api/routes/[id]/places`：实现是"先删后插"（`RouteResultClient` 注释已说明）。两个并发请求会不会互相覆盖导致丢地点？有没有基于版本号/事务的保护？
4. **新建路线** `POST /api/routes`：连点两次会不会建两条？
5. **游客转正** `POST /api/try/promote`：连点"保存路线"会不会落两条路线 / 两次扣配额？
6. **多标签页**：`RouteResultClient` 的 `saveOrder` 是 600ms 防抖；两个标签页同时编辑同一路线会怎样？
7. **游客限流** `checkGuestRateLimit`：内存 Map 的读改写非原子，并发下会不会多放行？（评估影响，不修）

## 6. 明确禁止

- 不得修改任何源码、SQL、迁移
- 不得对真实库发起写请求或并发压测
- 不得把推测写成事实

## 7. 交付格式（`docs/concurrency-audit.md`）

每项一条，包含：
- 场景（什么操作 × 什么并发）
- 现状（代码怎么处理的，`文件:行`）
- 结论：**安全 / 有风险 / 未知**，并标 `[已确认]`/`[高度可能]`/`[未知]`/`[风险]`
- 证据（SQL 约束、状态机判断、事务边界）
- 若"有风险"：后果 + 最小修复建议（不改代码，只给方案）

## 8. 验收标准

- [ ] 7 项都有结论，无"待分析"
- [ ] 每项都有 `文件:行` 证据
- [ ] 至少指出 2 处真实风险（若无风险则需说明为什么安全，并给出证据）
- [ ] 检查了数据库层约束（唯一索引/检查约束/触发器），不只是应用层
- [ ] 零源码改动（`git diff` 只有 docs）
- [ ] `npm run test:run` 仍通过（回归确认没被影响）
