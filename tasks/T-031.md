# T-031 启动器前置门禁：持续检测自建 Supabase，通了才继续

> 用户 2026-10-24：双击启动 App 时，先检测 Windows 上的自建 Supabase / Docker 是否已启动；
> 未启动就明确提示原因，并**持续检测**，等启动完成后自动继续。

## 1. 目标

`启动项目.command` 在启动 dev server **之前**，进入「等待数据库就绪」阶段：

1. 从 `Project/.env.local` 读取 Supabase 地址（只读，不打印密钥）
2. 每 **5 秒**探测一次，能区分三种失败原因，并给出**可操作**的中文提示
3. 探测通过（REST 返回 200）→ 打印「✅ 数据库已就绪」→ 继续原有启动流程
4. 未通过 → 循环检测，显示已等待时长与当前判定；**不退出**；提示可 Ctrl+C 放弃
5. 不得在等待期间启动 dev server（避免页面起来了但库没起来，用户以为坏了）

## 2. 三态判定（务必区分，提示语不同）

| 状态 | 判定方法 | 提示文案要点 |
|---|---|---|
| A. Windows 电脑不可达 | `ping -c1 -W1 <host>` 失败 且 TCP 8000 不通 | 「Windows 电脑可能没开机/不在同一 Wi-Fi」→ 让用户开机或连同一网络 |
| B. 电脑在线但 Docker/Supabase 没起 | ping 通 或 `nc` 主机可达，但 8000 端口不通 | 「电脑在线，但 Docker Desktop / Supabase 容器没启动」→ 让用户启动 Docker Desktop 与 supabase 容器 |
| C. 端口开着但服务没就绪 | 8000 通，但 REST 200 拿不到（超时/5xx） | 「容器在启动中或服务异常，继续等待」 |

## 3. 不做什么

- 不改应用代码、不启动/管理 Windows 上的 Docker（跨机器无法直接控制）
- 不打印 `.env.local` 里的任何密钥值
- 不做开机自启
- 不改 `deploy/` 脚本

## 4. 现状

| 项 | 值 |
|---|---|
| 启动器 | `启动项目.command`（T-030 产出，已可双击启动） |
| 现有行为 | 跑 `npm run check:env`，失败**仅警告**后继续启动 |
| Supabase 地址 | `Project/.env.local` 的 `NEXT_PUBLIC_SUPABASE_URL`（如 `http://192.168.1.11:8000`） |
| 探测接口 | `GET {SUPABASE_URL}/rest/v1/cities?select=name&limit=1`（用 anon key，200 即就绪） |

## 6. 明确禁止

- 等待期间启动 dev server
- 死循环无任何输出（必须每轮打印状态或计时）
- 打印密钥；把 URL 里的 key 写进日志
- 用 `sleep 1` 高频探测（用 5 秒）
- 修改 `.env.local`

## 7. 验收标准

- [ ] Supabase 正常时：直接打印「✅ 数据库已就绪」并继续启动（不阻塞）
- [ ] Supabase 不可达时：打印 A/B/C 对应提示 + 已等待时长，并**持续重试**
- [ ] 恢复可达后（无需重开窗口）：自动继续启动 dev server
- [ ] 等待期间不启动 dev server（`lsof -i:3000` 无监听）
- [ ] 不打印密钥；`bash -n` 通过
- [ ] 提供测试用覆盖变量（如 `LYYTX_SUPABASE_HOST_OVERRIDE`），便于无 Windows 环境下验证 A 状态（文档里标注仅调试用）

## 8. 测试方案（Harness 验收）

1. 正常态：直接运行 → 应立即通过并启动
2. 用一个不存在的 host 覆盖变量 → 应进入持续检测并打印 A 类提示（观察 10–15 秒，确认每 5 秒一轮）
3. 中断（Ctrl+C）→ 退出码正常、无残留进程

## 9. 失败恢复

`git revert <commit>`；启动器为本地脚本，无运行时副作用。

## 10. 风险等级

**低**。
