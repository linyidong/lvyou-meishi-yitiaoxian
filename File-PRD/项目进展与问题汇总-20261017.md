## 五、自建 Supabase 的形态与接线（v3 新增，重要）

### 5.1 形态

用户采用的是**官方 docker-compose 自建版**（`supabase/docker`），**不是 Supabase CLI 版**，因此：

- 那台 Windows 机上**没有 `supabase` 命令**（`supabase status` 报"不是内部或外部命令"属正常现象，**不需要安装 CLI**）。
- 端口与 CLI 版不同：**8000 = Kong 网关**（同时提供 REST、Auth 与 Studio 后台），**5432 = Postgres**；**没有** 54321/54323 这些端口。
- 后台（Studio）入口：`http://192.168.1.11:8000/`，会先弹出 **basic-auth 用户名/密码**（值在 Windows 机的 `supabase/docker/.env` 中的 `DASHBOARD_USERNAME` / `DASHBOARD_PASSWORD`）。

### 5.2 地址与端口

| 角色 | 地址 |
|---|---|
| 数据库主机（Windows 笔记本，常开） | `192.168.1.11`（**不回 ping**，Windows 防火墙默认禁止 ICMP，属正常） |
| Mac（开发机） | `192.168.1.12`，与上者同一 WiFi（`192.168.1.0/24`，网关 `.1`） |
| 应用连接地址（Mac 侧 `NEXT_PUBLIC_SUPABASE_URL`） | `http://192.168.1.11:8000` |
| REST 接口 | `http://192.168.1.11:8000/rest/v1/` |
| Auth 接口 | `http://192.168.1.11:8000/auth/v1/` |
| Studio 后台 | `http://192.168.1.11:8000/`（需 basic-auth） |
| Postgres（直连，一般用不到） | `192.168.1.11:5432` |

### 5.3 密钥

- Mac 侧 `Project/.env.local` 中的 `NEXT_PUBLIC_SUPABASE_ANON_KEY` / `SUPABASE_SERVICE_ROLE_KEY` 必须来自 Windows 机 `supabase/docker/.env` 的 `ANON_KEY` / `SERVICE_ROLE_KEY`（JWT 格式，**与云端新版 `sb_publishable_…` 格式不同**）。用户已自行填入，**不要在对话中回显**。
- 自建版默认密钥是公开的演示值，**仅可用于局域网开发**；阶段 ⑨ 上线前必须重新生成。

### 5.4 局域网通路已实测可用（2026-10-17）

| 测试 | 结果 |
|---|---|
| Mac → `http://192.168.1.11:8000/` | 401「Missing username and password」= 网关存活，缺 basic-auth |
| Mac → `/rest/v1/cities?select=name&limit=3` | ✅ 返回 `北京 / 上海 / 天津` = 网络 + 密钥 + 数据库 + RLS 全通 |
| Mac → `192.168.1.11:5432` | ✅ 可连接 |
| 应用注册接口（真实建号） | ✅ 返回 `{ok:true, needConfirm:false, redirect:"/profile"}`，`users` 表立即出现该行且 `role=user` |
| 应用登录接口（该账号） | ✅ 返回 `{ok:true, redirect:"/profile"}`（**不是** `/admin`） |
| 应用登录接口（假账号） | ✅ 返回「邮箱或密码不正确」= 请求真的到达 GoTrue 并完成校验 |

**结论：不需要 Tailscale、也不需要改动防火墙或端口映射**——Docker Desktop 默认已把端口发布到局域网。Tailscale 仅用于"用户带着 Mac 离开同一 WiFi 时"的异地访问，属可选加分项（安装包曾下载到 `~/Downloads` 后由用户删除，需要时重新下载：`https://pkgs.tailscale.com/stable/Tailscale-latest-macos.pkg`，该域名实测可达）。

## 八、已知问题与教训（归档，避免重复踩坑）

| 编号 | 教训 |
|---|---|
| L1 | 登录失败曾被统一显示成「邮箱或密码不正确」，把网络故障也归入其中，导致用户误删重建账号。现分三类：连不上后端 / 邮箱未确认 / 密码错误。**再遇登录失败先看提示类别。** |
| L2 | 云端项目 ref 曾被抄成 18 位（少 2 位）导致域名不存在。人工抄写 key/ref 一律用复制按钮。**云端已弃用，此项仅作归档。** |
| L3 | 本机网络对 `*.supabase.co` 做 TLS 重置（宽带与手机热点均不通）→ 这就是改用局域网自建的根因。**不要再尝试直连云端 Supabase。** |
| L4 | Node 不使用系统代理；浏览器能开 Supabase 后台是因为后台在 `supabase.com` 域，与 `*.supabase.co` 被区别对待。 |
| L5 | **Windows 防火墙默认不回 ping**，导致局域网扫描漏掉那台机器（找不到设备≠设备不在）。定位应改用"直接探端口"。 |
| L6 | 自建版**没有 `supabase` CLI**，端口是 **8000/5432**，不是 54321/54323。看到"不是内部命令"不要去装 CLI。 |
| L7 | 自建版未配 SMTP 时，官方 `signUp` 会报 `Error sending confirmation email`。**已改用 `admin.createUser({ email_confirm: true })` 绕过**（见 L12）。若日后改回 `signUp`，必须先配 SMTP 或设 `ENABLE_EMAIL_AUTOCONFIRM=true`。 |
| L8 | Docker Desktop 默认已把端口发布到局域网，**往往不需要额外改防火墙/端口映射**；先实测再动手。 |
| L9 | Trae 沙箱内网络不可用；跨网测试一律走 `osascript -e 'do shell script …'`（输出写文件再读，避免中文乱码）。 |
| L10 | 系统提示"文件被用户删除"**可能是误报**；一律先用 `git status` 或直接读文件核实，不要据此重建。 |
| L11 | `apply_all.sql` 头部注释曾写"001~013"（实际已含 014），已修正，避免后续重新生成时丢掉 014。 |
| L12 | **验证触发器不要只查 `pg_trigger`**：PostgREST 读不到 `pg_catalog`，从 Mac 侧无法直接查。更可靠的做法是**行为测试**——用普通用户令牌调 `PATCH /rest/v1/users` 改 `role`/`member`，被 `FORBIDDEN` 挡住即证明触发器在生效（改完务必用 `service_role` 复查并还原）。 |
| L13 | 自建版**没有 SMTP 也能注册**：用 `service_role` 的 `auth.admin.createUser({ email_confirm: true })` 建号，再 `signInWithPassword` 写会话即可。注意上线后要改回邮箱确认。 |
| L14 | zsh 里 `UID` 是内置整数变量，脚本中赋字符串会报 `bad math expression`；变量名一律避开 `UID`（改用 `TARGET_ID` 之类）。 |
