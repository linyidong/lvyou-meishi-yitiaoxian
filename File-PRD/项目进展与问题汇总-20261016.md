## 五、当前最大阻塞：本机无法访问托管版 Supabase（已三重实测）

### 5.1 目标地址

云端项目 ref：`jtmtfmlmbzefworvwqlf`（20 位）。据此得到：
- 应用接口域：`https://jtmtfmlmbzefworvwqlf.supabase.co`（**受阻的就是这个域**）
- 后台管理域：`https://supabase.com/dashboard`（可正常打开）

### 5.2 实测证据（2026-10-16）

| 测试方式 | 目标 | 结果 |
|---|---|---|
| Chrome | `…supabase.co/rest/v1/` | ✅ 正常返回 JSON（`{"message":"No API key found in request"}`） |
| Safari | 同上 | ❌「服务器意外中断了连接」 |
| 系统 curl（LibreSSL） | 同上 | ❌ 连接中断 |
| **Node（应用本体）** | 同上 | ❌ 连续 3 次 `ECONNRESET`（TCP 已连上 Cloudflare，**TLS 握手阶段被重置**） |
| IPv6 通路 | 同上 | ❌ 无可用 IPv6（仅解析到 IPv4） |
| **手机热点下 curl** | 同上 | ❌ 返回 `000`（宽带与移动网络两条线路均不通） |

### 5.3 结论

- 该网络对 `*.supabase.co` 的**程序型 TLS 连接**做重置/拦截；浏览器（Chrome）例外，但**应用所有数据库与登录请求都由服务端 Node 发起**，因此应用不可用。
- 影响：登录、注册、收藏、路线、个人中心、管理端**全部不可用**；页面能打开但无数据。
- 已排除：密码错误、邮箱未确认、账号不存在、代码缺陷、代理/VPN 干扰（用户确认未开代理，且开启代理也不解决）。
- 派生结论：**国内终端用户将来会遭遇同样问题** → 必须国产化（第六节）。

### 5.4 排障过程中被证实"冤枉"的历史操作（勿重复）

1. 用户按"密码错误"提示**删除并重建**了云端管理员账号 `1035940028@qq.com`（新 UID `bef74c8c…`）——此操作是多余的，根因是连不上而非密码错。
2. 重建后的新账号**未执行** `role='admin'` 提权 SQL。且云端项目即将弃用，**不要再补这条 SQL**（本地新库会重新建号，见第七节 B 组）。

`Supabase` 官方**没有中国区**，"数据在境内 + 国内用户可访问"无法通过官方托管满足。

| 选项 | 月成本 | 代码改动 | 数据在境内 | 结论 |
|---|---|---|---|---|
| **A. 在国内云服务器上自建 Supabase** | ¥80~120（2C4G 轻量云） | 几乎为零，只改地址 | ✅ | **用户已采纳** |
| B. 换国内托管后端（阿里云 RDS / 腾讯云开发） | 视用量 | 登录 + 数据访问层需重写 | ✅ | 暂不考虑 |
| C. Supabase 官方绑自定义域名 | $25 | 零 | ❌ | 被否（违背数据境内要求） |

### 6.2 用户拍板的两阶段路线

| 阶段 | 内容 | 花费 | 归属 |
|---|---|---|---|
| **阶段 1（进行中）** | 在**局域网另一台常开的 Windows 笔记本**上用 Docker 自建 Supabase；Mac 上的应用连过去 → 开发与验收全部在局域网内完成，不再受外网阻断影响 | ¥0 | 用户已安装 Docker 并报告"自建完成"（待验证） |
| **阶段 2（未开始）** | 上线时把**同一套**自建 Supabase 部署到国内云服务器（+ 域名 + ICP 备案），应用同机部署；数据搬迁 = 跑 `apply_all.sql` + 导用户数据行 | 服务器 ¥80~120/月 + 域名 ¥50/年 | 我出脚本，用户买机器与备案 |

- 关键收益：本地与线上是**同一套**，不构成二次改造；上线时不需要复杂的数据库 dump 迁移。

- 已知代价：① 助手**无法操作那台 Windows 机**，所有步骤只能由用户手动执行并截图回诊；② 那台机**必须常开**，一关机应用立即登录失败（表象与"连不上服务器"相似，但原因不同）。
